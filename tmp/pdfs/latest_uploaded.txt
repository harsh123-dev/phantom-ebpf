Abstract—Cloud-native applications rely on third-party com-
ponents whose runtime behavior can change after deployment.
Monitors and software bills of materials (SBOMs) capture dif-
ferent evidence; linking events to components and causal respon-
sibility remains difficult. PHANTOM implements SBOM verifi-
cation interfaces, eBPF event collection, variable-order Markov
behavioral contracts, a time-decayed Behavioral Dependency
Graph (BDG), and a DoWhy-based causal-estimation pathway
and an XGBoost PCEPS scorer. Its design combines image-
and PURL-scoped contract generation with a temporal causal
projection that returns not_identifiable when specified
identification checks fail. This is an integration design, not a
claim that these mechanisms are new or that component-level
causal attribution has been validated. In an evaluation of six
completed attack runs across the two tested supply-chain attack
families, PHANTOM recorded drift events with mean latency
15.74 seconds, median 5.52 seconds, and linearly interpolated
95th percentile 54.72 seconds. Three SolarWinds-style injections
failed before an attack phase. The saved event records lack re-
solved PURL/SBOM bindings, and the dataset contains no benign
controls; thus attribution accuracy, false-positive rate, calibrated
prediction, and runtime overhead remain unestablished. These
preliminary results document event presence and latency only.
PHANTOM contributes an implementable, uncertainty-aware
research pathway whose component mapping and causal value
require controlled evaluation.

I. I NTRODUCTION
Cloud-native applications assemble services from third-
party packages, container images, build tools, and deployment
configuration. That composition shortens development cycles,
but it also creates several points where the delivered software
can differ from what an operator expected. A dependency may
be substituted, a build artifact may be altered, or a legitimate
update may change runtime behavior. An SBOM records
component inventory and relationships; runtime monitoring
observes what executes. Neither view alone answers whether
an observed process, file access, or network connection came
from a particular package or whether a package change caused
the behavior.
The XZ Utils incident illustrates the problem. Modified
build scripts introduced malicious functionality into selected
liblzma release artifacts, and the resulting behavior affected
an OpenSSH authentication path. The compromise became
public after Andres Freund investigated anomalous CPU use
and related symptoms in SSH testing [1], [2]. A runtime event
such as an unexpected execution or network connection could
be useful evidence in a similar incident, but that event alone
would not identify the responsible package. A process may
load code from several packages, inherit configuration from
its workload, or perform unusual behavior after a legitimate
deployment change. Attribution therefore depends on prove-
nance mapping and explicit assumptions about the causes of
observed behavior.
For example, when a runtime monitor reports an unexpected
execution, its event record may identify the process and
operation. The record does not by itself establish whether code
associated with ‘pkg:pypi/lz4@4.3.2‘ caused the execution or
whether a configuration change in the same container explains
it. PHANTOM investigates an architecture for joining these
evidence types: contracts keyed by image digest and PURL,
event relationships in a Behavioral Dependency Graph (BDG),
and a causal-estimation pathway that abstains when configured
identification checks fail. The available attack records do
not contain resolved PURL/SBOM bindings, so the intended
component-level link is implemented as a system pathway but
is not demonstrated by these experiments.
This paper makes three implementation and evaluation
contributions, with evidence scopes stated separately:
• Implemented and observed at the event level: the reposi-
tory contains a variable-order Markov contract-generation
pipeline, BIC order selection, and KL-divergence scoring.
In six completed attack runs across two families, the
saved records contain drift events within the recorded de-
tection windows; their median injection-to-event latency
is 5.52 s. The records do not establish that those events
were bound to the responsible SBOM component.
• Implemented and tested structurally: the repository con-
tains a typed, time-decayed BDG and a temporal DAG
projection with a fixed semantic tier ordering. The local
test run completed with 454 passed and one skipped
test across the core library and five services. These unit
tests exercise code paths, including cycle handling and
abstention cases; they do not prove causal correctness or
component attribution in deployment.
• Implemented, awaiting experimental validation: a
DoWhy adapter and a 16-feature PCEPS training,
calibration, and scoring pathway are present. The adapter
returns not_identifiable for specified failures
rather than using a correlation fallback. The saved\n\n--- PAGE 2 ---\nrun artifacts contain no component-level oracle labels,
trained scoring model, or held-out predictive results.
A. Design Distinctions and Research Claims
PHANTOM’s research question concerns the interfaces
among event collection, package identity, behavioral deviation,
and causal analysis; the use of eBPF, Markov models, graphs,
DoWhy, or XGBoost alone is not claimed as novel. The
implementation makes three testable design choices. First,
contract-generation requests carry an image digest and PURL,
enabling component-scoped model records when event-to-
component identity is available. Second, the causal projection
orients selected within-window edges using an explicit seman-
tic tier hierarchy, while preserving the underlying BDG and
withholding queries that remain cyclic. Third, identification
failures produce the first-class status not_identifiable,
rather than an association score presented as a causal effect.
These are implementation properties and candidate research
contributions, not a verified claim that PHANTOM is the first
system to make them or that the tier assumptions recover true
causal structure. The saved experiment records lack the pack-
age bindings and independent labels needed to test whether
these choices improve attribution.
The evaluation is intentionally narrower than a detector
benchmark. Six completed attacks produced event-positive
records; three SolarWinds-style injections failed before an
attack phase. No benign control windows were saved, so false-
positive rate and precision cannot be calculated. The baseline
log documents a dry run rather than comparable Falco, Trivy,
or Isolation Forest results. Mean latency was 15.74 s, median
5.52 s, and linearly interpolated P95 54.72 s; the first XZ run
took 70.332 s, and the available logs do not explain the delay.
Reporting these limits makes clear which observations the
present artifacts support and which research questions remain
open; it does not turn the six-run dataset into evidence of
general detection performance.

II. B ACKGROUND AND RELATED WORK
A. Software Supply Chain Attacks
Supply-chain compromises exploit trust relationships be-
tween producers, build systems, and consumers. SolarWinds
disclosed SUNBURST in December 2020 after malicious
code had been inserted into the Orion build pipeline and
distributed inside digitally signed updates. The backdoor re-
mained dormant before initiating selective network commu-
nications, and its delivery through a trusted vendor update
complicated detection based on package reputation alone [3],
[4]. Log4Shell, disclosed in December 2021 as CVE-2021-
44228, was different: attacker-controlled strings could trigger
JNDI lookups in vulnerable Log4j configurations, potentially
leading to remote code execution. The library was widely
embedded transitively, so asset owners often did not know
which services loaded it [5], [6].
The XZ Utils compromise became public on March 29,
2024, when a developer found anomalous CPU behavior
during SSH testing. Modified build scripts enabled a back-
door in selected release artifacts, despite source review and
package provenance appearing ordinary to many downstream
consumers [1], [2]. These incidents differed in mechanism,
but each challenged a different monitoring assumption: SUN-
BURST used delayed, selective execution; Log4Shell was
activated by input and dependency reachability; XZ altered
build outputs and targeted a sensitive library interaction. At
the kernel boundary, each could produce observable evidence
such as unexpected process execution, file access, or outbound
connections, but no single event signature would uniquely
establish the responsible package. Kernel evidence can narrow
the explanation; it cannot by itself prove software provenance.
B. eBPF-Based Runtime Security
Falco uses eBPF in cloud-native systems to monitor Linux
and report suspicious activity [7]. It lets users create rules
through a policy rule engine, which is useful for recognizing
known malicious patterns and policy violations. Its coverage,
however, depends on the rules available: behavior outside the
configured rules may go undetected.
Tetragon also uses eBPF to monitor operating-system ac-
tivity, including process execution and network use, for se-
curity observability and policy enforcement [8]. It provides
Kubernetes-aware controls, while linking its events to a spe-
cific SBOM component requires additional identity mapping
and analysis.
Tracee provides Linux runtime security and forensic ca-
pabilities using eBPF, including event collection and policy-
based detection [9]. Its event stream can support investigations,
but collecting evidence is distinct from estimating whether a
specific package change caused an observed deviation. None
of these tools can answer which specific SBOM component
substitution caused an observed behavioral change, because
none maintain a runtime model linking observed events to
signed software component identities.
C. Software Bill of Materials and Runtime Drift
CycloneDX defines a machine-readable bill of materials
for software components, dependencies, and related supply-
chain metadata [10]. The NTIA minimum-elements work also
established a practical baseline for SBOM fields and exchange
[11]. Such formats make component inventories more useful,
but a manifest remains a statement about declared or observed
contents at a point in the build or scan process. It is not a
continuous record of behavior after deployment.
Anchore Enterprise uses SBOM-centered analysis for vul-
nerability and supply-chain management [12], while Ox Se-
curity describes software supply-chain risk analysis across\n\n--- PAGE 3 ---\ndevelopment and production contexts [13]. Those capabilities
address important inventory and risk questions. PHANTOM
focuses on a narrower gap: the package can remain in the
SBOM under the same name and version while its runtime
behavior changes. A reliable response therefore needs both
artifact identity and live behavior, with uncertainty retained
when an event cannot be mapped confidently to a component.
This distinction matters because package identity is not
a behavioral invariant. A PURL normally identifies package
type, namespace, name, and version; it does not prove that a
deployed file is byte-for-byte identical to reviewed source or
artifact. Digest pinning and signature verification can establish
stronger provenance, but even a validly signed package may
contain harmful code, as supply-chain incidents have demon-
strated. Runtime observation complements those controls by
checking what loaded software does in the environment where
it executes. It cannot replace provenance: an event-to-PURL
association is only as reliable as the image metadata, process
mapping, and file attribution used to make it. A practical
system must preserve these provenance links and expose
missing links to the analyst rather than silently assigning an
event to the nearest package.
The same distinction shapes PHANTOM’s handling of
benign change. Library upgrades, feature flags, configuration
changes, and workload autoscaling can all alter event fre-
quencies without indicating compromise. A contract trained
on one operating envelope may therefore generate alerts when
a service changes legitimately. Versioned contracts, workload
context, and analyst review are required to separate routine
evolution from suspect drift. We treat contract violation as
evidence requiring explanation, not a verdict that a package
is malicious. This policy is particularly important for services
whose legitimate behavior is adaptive or customer-specific.
D. Causal Inference Applied to Security
Cloud incident root-cause systems combine operational sig-
nals to help explain service incidents; RCACopilot, for exam-
ple, uses an LLM to predict a root-cause category and produce
an explanation from incident diagnostics [14]. Earlier host-
telemetry research programs also study system-level evidence
and provenance [18]. Graph-based anomaly detection similarly
uses relationships among entities to identify patterns that are
difficult to see in isolated events. An anomaly score or ranked
explanation does not by itself identify an intervention effect.
PHANTOM uses Pearl’s intervention notation and
DoWhy’s causal workflow to represent assumptions behind
a component-level estimate [15], [16]. The distinction is
between observing a component substitution and intervening
on that substitution while holding an identified adjustment
set fixed. Applying a general causal-inference library to
runtime evidence is an integration; novelty depends on the
graph construction, identification checks, mapping quality,
and evaluation rather than the use of DoWhy alone.
SBOM generators establish inventories; vulnerability scan-
ners connect inventories to advisories; runtime monitors col-
lect events and apply policies; incident tools correlate opera-
tional signals. PHANTOM targets the interfaces among these
layers. It does not replace provenance verification, vulnerabil-
ity management, or runtime enforcement. The repository uses
PURL identifiers as component keys, following the package
URL specification [26].
Contract generalization remains an open question. Evalu-
ation should compare contracts keyed only by PURL with
models conditioned on workload role or service mode, and
should compare temporal Markov models with frequency
baselines using matched event access.

F . Gap This Paper Addresses
The existing system categories address different parts of
the problem: runtime event collection and policy enforcement,
component inventory and provenance, or incident-level diag-
nosis. PHANTOM explores an interface among these cate-
gories by representing image/PURL-scoped contracts, runtime
relationships, and an explicit causal-query abstention status
in one implementation. This paper does not claim that no
published system offers any of these capabilities, nor that
the combination has been proven to improve attribution. The
empirical question is whether resolved component identity
and a defensible temporal causal model can support more
accurate, useful explanations than event presence or graph
ranking alone. The current records cannot answer that question
because they lack PURL-bound events and component-level
ground truth.

B. Behavioral Contract Generation
For a component identified by a PURL, the contract-
generation use case retrieves training sequences scoped by
image digest, PURL, and time interval. A token is a four-tuple
(event type, operation class, resource class, privilege class).
The Markov model operates over the observed token alphabet
plus reserved unknown/resource tokens. The implementation
does not by itself establish that the training interval contains
only normal behavior; that interval and its approval must be
controlled by the operator.
For each context h, the model estimates next-token prob-
abilities. Candidate orders are compared using BIC with
qk = |Hk|(|Σ| − 1) parameters, and contexts are pruned
when their local BIC does not improve over a retained suffix.

C. Behavioral Dependency Graph
We define the BDG as G = (V, E, ϕ, ψ), where V is a typed
entity set, E is a typed multiedge set, ϕ maps nodes to ob-\n\n--- PAGE 5 ---\nserved attributes, and ψ maps edges to event time, confidence,
and weight. Node types include workload, container, process,
PURL, file, network endpoint, contract, and drift event. Imple-
mented relations include runs, executes, belongs_to,
reads, writes, connects_to, derived_from, and
violates. Multiple edges are retained; the implementation
uses a NetworkX MultiDiGraph representation.
At each observation time, an edge weight decays according
to
we(t) = λ(t−tprev)/∆ we(tprev) + qe, (3)
where 0 < λ < 1 controls forgetting, ∆ is the time scale, and
qe is the new evidence contribution. The temporal projection
assigns semantic variables to six implemented tiers: environ-
ment/RBAC/image (0), component version (1), process behav-
ior (2), file/network/privilege behavior (3), contract deviation
(4), and runtime SBOM drift (5). In a single time window,
the implementation permits an edge only from a lower to
a higher tier; cross-window edges point from the earlier to
later window. This fixed ordering is a modeling assumption
motivated by the hypothesized supply-chain sequence, not
evidence that the ordered variables are causally related in every
workload. It can orient simultaneous observations to yield a
DAG, but does not by itself establish identification or causal
truth. The BDG retains cycles because runtime interactions can
be cyclic. Projection code conservatively excludes unsupported
orientations and withholds attribution when an unresolved
cycle involves the treatment or outcome.
D. Structural Causal Attribution
The estimator represents a candidate component change as
treatment S, a binary drift outcome as D, and measured pre-
treatment covariates as X. The target is an average treatment
effect E[D | do(S = 1)] − E[D | do(S = 0)] under the
supplied causal graph and adjustment set. The outcome follows
from the input causal observations; covariates are supplied by
the caller.
The BDG projection expands semantic variable classes
across a fixed number of windows. Edges are added across
strictly increasing time windows, or within a window when
a hard-coded semantic tier increases. The SCM builder
then collapses window labels to semantic variable names,
adds treatment-to-outcome and covariate-to-treatment/outcome
edges, checks variation and a positivity rule, and serializes
the graph for DoWhy. DoWhy identification is requested with
unidentifiable effects disallowed [15], [16]. The implemen-
tation returns not_identifiable on treatment/outcome
cycles, no variation, positivity failure, construction, identifica-
tion, or estimation errors. Tests exercise cycle and no-variation
abstention paths; these tests validate software behavior under
constructed inputs, not the correctness of causal assumptions
in deployment.
For completed models, the configured estimator returns an
ATE and, when available, an interval. The pathway attempts a
treated-cohort counterfactual and runs random-common-cause,
placebo-treatment, and data-subset refutations. Its confidence

V. E VALUATION
A. Experimental Setup
The checked-in dataset contains nine JSON records dated
September 5, 2026. Six records contain a completed attack
phase: three ‘xzutils-001‘ runs and three ‘dep-confusion-001‘
runs. Three SolarWinds-style ‘solarwinds-001‘ records report
‘inject() returned False‘ and have no attack phase. They are
failed trials, not detection outcomes. The successful records
include injection and first-event timestamps, raw drift-event
records, and phase metadata. The recorded detection window
is 120 s after injection, as specified in the raw scenario records
and evaluation code. No benign controls are present. Although
the run script describes a planned EKS setup, the raw files do
not provide a complete cluster/kernel/container/image-digest
manifest. The saved event records identify a cluster name
but have ambiguous or missing pod identity and no SBOM
binding.

C. RQ2: Causal Attribution Accuracy
The checked-in aggregate reports attribution accuracy of
1.0, but the underlying records do not contain per-run pre-
dicted PURLs or a comparison with the oracle target PURL.
All saved drift events have ambiguous or missing identity,
null PURL/SBOM fields, and unknown workload identifiers.
Component identity and causal correctness therefore cannot
be verified, and no attribution accuracy is reported.
D. RQ3: PCEPS Prediction
The PCEPS source implements feature extraction, XGBoost
training, Platt scaling, Brier/ECE calculations, and scoring. No
trained PCEPS model, calibration artifact, scored windows,
labels, or metric output supporting the manuscript’s former
AUC/Brier values was found. No predictive-performance re-
sult is reported. The score’s future-outcome interpretation
requires a separate prospective evaluation.
E. RQ4: Overhead
The saved CPU, memory, and event-lag snapshots are all
zero. No raw Prometheus samples or measurement provenance
accompany them. These records cannot establish zero resource
cost or a particular event-loss rate; runtime overhead remains
unmeasured.
F . Threats to Validity
G. Benign Control Design and Current Gap
Benign controls are required to estimate how often or-
dinary workload changes trigger the event or contract\n\n--- PAGE 7 ---\npipeline. A future study should include routine package up-
dates, load changes without component changes, and pod
restart/autoscaling episodes. These controls should use the
same observation duration and instrumentation as attack runs,
with labels fixed before analysis. Until these runs are collected,
false-positive rate, precision, specificity, and F1 are undefined;
an event-positive fraction of 6/6 is not a recall estimate because
its event oracle does not require a correctly attributed attack.
These three scenario classes are a proposed protocol, not
verified existing runner functionality. The project repository
and saved experiment set do not establish that benign-update,
benign-load, and benign-restart automation has been imple-
mented or executed. A future evaluation should pre-register the
workload, contract version, event labels, and alert threshold,
then repeat each class under matched workload and deploy-
ment conditions. Sample size should be selected from the
desired confidence interval rather than treating three runs per
class as automatically sufficient.
The current data support only that drift events were recorded
during six completed attack windows. They do not bound
benign alert rates or establish attack detection accuracy. The
three failed SolarWinds-style injections must be fixed and
rerun before that attack family can be assessed.
H. Threats to Validity
The six completed runs cover two attack families and
use a run-level event-presence label; event presence does not
establish that a malicious event was attributed to the injected
component. The raw records have no benign controls, all-
zero overhead snapshots, unresolved component identity, and
no reproducibility manifest with kernel/runtime versions and
image digests. Three attack injections failed. The baseline log
documents a dry run: Falco and Trivy setup were skipped and
Falco alert logs were missing. Trivy is a static vulnerability
scanner, so a runtime detection comparison requires a sepa-
rately defined task and labeling rule. PCEPS model/calibration
outputs and causal ground-truth comparisons are absent. These
gaps preclude claims of comparative accuracy, causal attribu-
tion quality, calibration, and operational overhead.
VI. C ONCLUSION
PHANTOM demonstrates an implemented pathway that
connects SBOM-facing contract generation, eBPF event col-
lection, typed graph maintenance, and a causal-estimation
interface with explicit abstention. A local run of the core and
five service test suites completed with 454 tests passed and
one skipped. This verifies exercised software behaviors, not
the validity of component-level causal claims in a live deploy-
ment. The experiment records show event-positive outcomes
in six completed runs, but do not validate package mapping,
attribution accuracy, prospective risk prediction, benign false-
positive behavior, or overhead.
The immediate evaluation priorities are benign controls, per-
run component-ground-truth records, repeatable SolarWinds-
style injections, matched baseline output, and a trained PCEPS
model evaluated on held-out labels. Kernel, Kubernetes, con-
tainer runtime, tool versions, image digests, and experiment
commit must be recorded with the rerun. No claim is made
that the infrastructure for all these experiments is already
implemented or ready to execute.
Supply-chain incidents expose a gap between declared soft-
ware inventory and observed runtime activity. PHANTOM
explores one way to represent that gap while making missing
identity and failed causal identification visible to an analyst.
Its present contribution is an implemented research prototype
and an auditable account of what the available tests and six
successful attack runs do—and do not—show. Controlled eval-
uation must establish whether its component-scoped contracts
and causal pathway produce reliable attribution beyond event
