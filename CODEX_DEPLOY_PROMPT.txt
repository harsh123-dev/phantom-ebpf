STEP 6 — DATABASE: Verify Migrations Ran Successfully
═══════════════════════════════════════════════════════════════════

STEP 7 — PORT FORWARD: Persistent, Self-Reconnecting API Gateway Tunnel
═══════════════════════════════════════════════════════════════════

IMPORTANT: All commands in Steps 7–9 run on your LOCAL Windows machine
(via Git Bash / the same terminal where you ran bootstrap.sh).
Do NOT SSH into EC2 — kubectl port-forward runs locally and tunnels to the cluster.

A plain `kubectl port-forward &` dies if the pod restarts or the connection drops.
Instead, write a self-healing reconnect loop and run it with nohup so it keeps
going even if the terminal loses focus.

7a) Write the reconnect loop script:

    cat > /tmp/pf_loop.sh << 'HEREDOC'
    #!/bin/bash
    # Self-reconnecting kubectl port-forward loop.
    # Runs forever; restarts within 5 seconds whenever the tunnel drops.
    echo "[pf_loop] Starting persistent port-forward for phantom-api-gateway:8080"
    while true; do
        echo "[pf_loop] $(date -u '+%Y-%m-%dT%H:%M:%SZ') -- Connecting..."
        kubectl port-forward svc/phantom-api-gateway 8080:8080 -n phantom 2>&1
        echo "[pf_loop] $(date -u '+%Y-%m-%dT%H:%M:%SZ') -- Tunnel exited (code $?). Reconnecting in 5s..."
        sleep 5
    done
    HEREDOC
    chmod +x /tmp/pf_loop.sh

    NOTE: This heredoc uses single-quoted 'HEREDOC' deliberately so that the
    $(date) and $? expressions are written literally into the script and only
    evaluate when the SCRIPT ITSELF runs — not when the cat command runs.

7b) Launch the loop with nohup so it keeps running after the terminal closes:

    nohup bash /tmp/pf_loop.sh >> /tmp/pf_loop.log 2>&1 &
    echo $! > /tmp/pf_loop.pid
    echo "Port-forward loop running as PID $(cat /tmp/pf_loop.pid)"

7c) Wait 8 seconds for the first connection to establish:

    sleep 8

7d) Verify the tunnel is alive and the API is responding:

    curl -s -o /dev/null -w "%{http_code}" http://localhost:8080/healthz

    NOTE: The PHANTOM liveness probe is at /healthz (NOT /health or /api/v1/health).
          It returns HTTP 200 with body {"status": "ok"} when the gateway is up.

    Acceptable responses:
      - 200 --> API is fully up
      - 401 or 403 --> API is alive but requires a bearer token (this is fine)

    NOT acceptable:
      - 000 or "Connection refused" --> the loop has not connected yet

    If you get 000 or connection refused:
      1. Check the process is alive:  kill -0 $(cat /tmp/pf_loop.pid) && echo ALIVE || echo DEAD
      2. Read the log:                tail -30 /tmp/pf_loop.log
      3. Check the pod is ready:      kubectl get pods -n phantom -l app=phantom-api-gateway
      4. If the PID is dead, re-run step 7b.

7e) To stop the port-forward loop at any time:

    kill $(cat /tmp/pf_loop.pid)

STEP 9 — VERIFY DETECTION: Confirm PHANTOM Caught the Attack
═══════════════════════════════════════════════════════════════════

After injecting the attack, wait 30 seconds and then query the PHANTOM API
to check if an incident (supply chain violation) was created:

    curl -s "http://localhost:8080/api/v1/incidents?limit=5" | python3 -m json.tool

You should see at least one incident in the response with status "open" or "confirmed".

Alternatively, check drift events (the eBPF agent posts events here as they happen):

    curl -s "http://localhost:8080/api/v1/drift-events?since=$(date -u -d '5 minutes ago' '+%Y-%m-%dT%H:%M:%SZ')&limit=20" \
        | python3 -m json.tool

    NOTE: The drift-events endpoint requires a mandatory ?since= datetime parameter
    in ISO 8601 format (e.g. 2026-01-01T00:00:00Z). It will return HTTP 422 without it.

If both return empty lists, check the eBPF agent is running and sending events:

    kubectl logs -n phantom -l app=phantom-ebpf-agent --tail=30
