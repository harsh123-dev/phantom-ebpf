═══════════════════════════════════════════════════════════════════
STEP 7 — SECURITY GROUP FIX: Enable kubectl port-forward and exec
═══════════════════════════════════════════════════════════════════

MANDATORY before starting port-forward. Without this, port-forward and exec
both fail with: "error upgrading connection: dial tcp ...:10250: i/o timeout"

WHY: EKS auto-creates a second AWS-managed cluster security group (separate from the
one we defined in Terraform). The control plane uses THIS managed SG to reach the
kubelet API on port 10250 on each worker node. Without an ingress rule from the
managed SG to our worker node SG, all kubelet traffic is silently dropped.

7a) Get the worker node security group ID:
    NODE_SG=$(aws ec2 describe-security-groups \
      --region ap-south-1 \
      --filters "Name=group-name,Values=phantom-dev-node" \
      --query "SecurityGroups[0].GroupId" \
      --output text)
    echo "Node SG: $NODE_SG"

7b) Get the AWS-managed EKS cluster security group:
    MANAGED_CLUSTER_SG=$(aws eks describe-cluster \
      --name phantom-dev \
      --region ap-south-1 \
      --query "cluster.resourcesVpcConfig.clusterSecurityGroupId" \
      --output text)
    echo "Managed Cluster SG: $MANAGED_CLUSTER_SG"

7c) Add the missing ingress rule:
    aws ec2 authorize-security-group-ingress \
      --region ap-south-1 \
      --group-id "$NODE_SG" \
      --protocol -1 \
      --source-group "$MANAGED_CLUSTER_SG"

    If you get "InvalidPermission.Duplicate", the rule already exists — continue.

7d) Verify (must be a non-empty JSON array):
    aws ec2 describe-security-groups \
      --region ap-south-1 \
      --group-ids "$NODE_SG" \
      --query "SecurityGroups[0].IpPermissions[?UserIdGroupPairs[?GroupId=='$MANAGED_CLUSTER_SG']]" \
      --output json

═══════════════════════════════════════════════════════════════════
STEP 8 — PORT FORWARD: Run in a Dedicated tmux Window
═══════════════════════════════════════════════════════════════════

KNOWN ISSUE: Port-forward processes launched with "nohup &" are reaped between
Codex tool invocations. The fix: run it in a dedicated tmux window which Codex
tool invocations cannot kill.

8a) Create a dedicated tmux window for the port-forward:
    tmux new-window -n pf
    tmux send-keys -t pf "kubectl port-forward svc/phantom-api-gateway 8080:8080 -n phantom" Enter

8b) Wait 5 seconds, then verify the tunnel from the main shell:
    sleep 5
    curl -s -o /dev/null -w "%{http_code}\n" --max-time 10 http://localhost:8080/healthz

    Expected: 200
    Not acceptable: 000 or "Connection refused"

8c) If curl returns 000, the port-forward may have disconnected. Check it:
    tmux capture-pane -t pf -p | tail -20

    If you see an error, re-send the command:
    tmux send-keys -t pf "" Enter
    tmux send-keys -t pf "kubectl port-forward svc/phantom-api-gateway 8080:8080 -n phantom" Enter
    sleep 5
    curl -s -o /dev/null -w "%{http_code}\n" --max-time 10 http://localhost:8080/healthz

STEP 10b — CREATE INCIDENT: Link Drift Events to a Confirmed Incident
═══════════════════════════════════════════════════════════════════

IMPORTANT: Incidents are NOT automatically created from drift events.
The causal engine updates an internal graph but does NOT auto-raise incidents.
You must explicitly POST an incident. This is by design — analysts confirm detections.

10b-1) Create the incident report via the API:
    curl -s -X POST "http://localhost:8080/api/v1/incidents" \
      -H "Content-Type: application/json" \
      -H "Authorization: Bearer dev-bypass-token-for-local-testing" \
      -d '{
        "title": "Supply Chain Attack Detected: Dependency Confusion on emailservice",
        "severity": "critical",
        "status": "open",
        "summary": "PHANTOM eBPF agent detected an unexpected executable and network beacon from emailservice consistent with a dependency confusion supply chain attack.",
        "drift_event_ids": [],
        "tags": ["supply-chain", "dep-confusion", "emailservice"]
      }' | python3 -m json.tool

    A successful response returns a JSON object with an "incident_id" UUID.
    Save it: INCIDENT_ID=<the uuid from the response>

10b-2) Verify the incident is visible in the list endpoint:
    curl -s "http://localhost:8080/api/v1/incidents?limit=5" | python3 -m json.tool

    You should see the incident with status "open" and severity "critical".

10b-3) Confirm the incident (mark as analyst-confirmed):
    curl -s -X PATCH "http://localhost:8080/api/v1/incidents/${INCIDENT_ID}" \
      -H "Content-Type: application/json" \
      -H "Authorization: Bearer dev-bypass-token-for-local-testing" \
      -d '{"status": "confirmed"}' | python3 -m json.tool

    Expected: response contains "status": "confirmed".
