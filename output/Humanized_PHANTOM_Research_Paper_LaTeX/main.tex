\noindent\textbf{Abstract,} Cloud-native applications are counting on third-party components whose runtime behavior can change after de-\\ployment. Monitors and software bills of materials (SBOMs) encapsulate distinct indication; linking events to components and causal responsibility remains diﬀicult. My point is, PHANTOM implements SBOM verification interfaces, eBPF event collection, variable-\\order Markov behavioral contracts, a time-decayed Behav-\\ioral Dependency Graph (BDG), and a DoWhy-based causal-\\estimation pathway and an XGBoost PCEPS scorer, in actual application. Its design combines image- and PURL-scoped contract generation with a temporal causal projection that returns not\_identifiable when stipulated identification checks fail; this is an integration design, not a claim that those mechanisms are new or that component- level causal attribution has been validated. In an evaluation of six completed attack runs across the two tested supply-\\chain attack families, drift events with mean latency 15.74 seconds, were recorded median 5.52 seconds by PHANTOM, and linearly interpolated 95th percentile 54.72 seconds. Three SolarWinds-\\style injections failed before an attack phase. The saved event records lack settled PURL/SBOM bindings, and the dataset comprises no benign controls; thus attribution accuracy, false-\\positive rate, adjusted prediction, and runtime overhead remain unestablished; these initial findings document event presence and latency only. PHANTOM contributes an implementable, uncertainty-aware research pathway whose component mapping and causal value need controlled eval-\\uation.

\section*{I. Introduction}
Cloud-native applications are gathering services from third-\\party packages, container images, build tools, and de-\\ployment configuration; that composition shortens devel- opment cycles; it also is creating a few points where the delivered software can differ from what an operator anticipated. A reliance may be swapped, a build artifact may be altered. And yet, a legitimate update may change runtime behavior. Malicious functionality was introduced into se-\\lected liblzma release artifacts by modified build scripts. The snag is shown by the XZ Utils incident. Neither view alone answers whether an noticeable process, file access, or network connection came from a particular package. An SBOM records component inventory and relationships; runtime monitoring is seeing what carries out. But still, whether a package change caused the behavior. And more, the resulting behavior impacted an OpenSSH authentication path. The compro-\\mise became public after Andres Freund assessed anomalous CPU use and related symptoms in SSH testing {[}1{]}, {[}2{]}. A runtime event such as an unexpected execution or network connection could be helpful proof in a akin incident. But that event alone wouldn\textquotesingle t spot the responsible package. A process may load code from several packages, inherit configuration from its workload, or perform unusual behavior after a legitimate rollout change. Attribution therefore rests on provenance map-\\ping and clear assumptions about the causes of gathered behavior. Like, when a runtime monitor reports an unex-\\pected execution, its event record may spot the process and operation. PHANTOM studies an architecture for joining these evidence types: contracts keyed by image digest and PURL, event relationships in a Behavioral Dependency Graph (BDG), and a causal-\\estimation pathway that abstains when configured iden-\\tification checks fail. \subsection*{A. Design Distinctions and Research Claims}
PHANTOM's research question concerns the interfaces among event collection, package identity, behavioral de-\\viation, and causal analysis; the use of eBPF, Markov models, graphs, DoWhy, or XGBoost alone isn\textquotesingle t claimed as novel. The implementation makes three testable design choices. First, contract-generation requests carry an im-\\age digest and PURL, allowing component-scoped model entries when event-to-component identity is available. Second, the causal projection orients selected within-\\window edges using an explicit semantic tier hierarchy, while preserving the coring BDG and withholding queries that remain cyclic. Third, identification failures generate the first-class status not\_identifiable, rather than an association score presented as a causal effect. These are implementation properties and candidate research contri-\\butions, not a verified claim that PHANTOM is the first framework to make them or that the tier assumptions recover true causal structure. The saved experiment records lack the package bindings and autonomous labels needed to test whether these choices raise attribution. The check is intentionally narrower than a detector benchmark. Six completed attacks produced event-positive records; three SolarWinds-style injections failed before an attack phase. No harmless control windows were saved, so false-positive rate and precision can\textquotesingle t be calculated. The baseline log documents a dry run rather than comparable Falco, Trivy, or Isolation Forest results. Mean latency was 15.74 s, median 5.52 s, and linearly interpolated P95 54.72 s; the first XZ run took 70.332 s, and the available logs don\textquotesingle t explain the delay. Reporting these limits makes clear which notes the present artifacts support and which research questions remain open; it doesn\textquotesingle t turn the six-run dataset into the proof of broad detection performance. \section*{II. Background and Related Work}
\subsection*{A. Software Supply Chain Attacks}
Supply-chain compromises exploit trust relationships between producers, build systems, and consumers. So-\\larWinds uncovered SUNBURST in December 2020 after malicious code had been inserted into the Orion build pipeline and distributed inside digitally signed updates. The backdoor remained inactive before beginning selec-\\tive network communications, and its delivery through a trusted vendor update complicated detection based on package reputation alone {[}3{]}, {[}4{]}. Log4Shell, shared in December 2021 as CVE-2021-44228, was mixed: attacker-controlled strings could trigger JNDI lookups in vulnerable Log4j configurations, potentially directing to remote code execution. The library was extensively embedded transitively, so asset owners often didn\textquotesingle t know which services loaded it {[}5{]}, {[}6{]}. The XZ Utils compromise became public on March 29, 2024, when a developer found unusual CPU behavior during SSH testing. Modified build scripts enabled a backdoor in chosen release artifacts, despite source review and package provenance appearing ordinary to many downstream consumers {[}1{]}, {[}2{]}. These incidents differed in mechanism, but each challenged a different monitoring assumption: SUNBURST used delayed, selective execu-\\tion; Log4Shell was switched on by input and reliance reachability; XZ altered build outputs and focused a sensitive library interaction. At the kernel boundary, each could produce observable evidence such as unexpected process execution, file access, or outbound connections, but no single event signature would uniquely establish the responsible package. Kernel evidence can narrow the explanation; it can\textquotesingle t by itself prove software provenance.
\subsection*{B. eBPF-Based Runtime Security}
Falco uses eBPF in cloud-native systems to monitor Linux and report suspicious activity {[}7{]}. It lets users create rules through a policy rule engine, which is helpful for rec-\\ognizing known malicious patterns and policy violations. Its coverage, though, depends on the rules available: behavior outside the configured rules may go undetected. Tetragon also uses eBPF to monitor operating-system activity, including process execution and network use, for security observability and policy enforcement {[}8{]}. It awarely controls, while linking its events to a specific SBOM component requires extra identity mapping and examination. Tracee offers Linux runtime security and forensic capabilities using eBPF, including event collection and policy-based detection {[}9{]}. These tools can provide valuable evidence and enforcement, while package-level attribution depends on the rolled out configuration and any identity-\\mapping integrations. Collecting events or enforcing a policy doesn\textquotesingle t by itself estimate whether a particular component change caused an gathered departure.

\subsection*{C. Software Bill of Materials and Runtime Drift}
CycloneDX defines a machine-readable bill of materi-\\als for software components, reliances, and related supply-chain metadata {[}10{]}. A practical baseline for SBOM fields and exchange {[}11{]} was also established by the NTIA minimum-elements work. Such formats make component invento-\\ries more good, but a clear remains a statement about declared or gathered contents at a point in the build or scan process. It isn\textquotesingle t a continuous record of behaviour after rollout; in turn, runtime evidence and sbom enforcement have been connected by prior work. Bomfather uses kernel-level eBPF observa-\\tion during the builds to spot reliances and build build artifacts; its scope is build-time dependency dis-\\covery rather than the post-deployment drift and causal-\\estimation process scrutinized here {[}29{]}. Crawford emphet al. describe enforcing SBOM constraints through Linux eBPF and IMA {[}30{]}, so these efforts make clear that run-\\time/SBOM integration isn\textquotesingle t, by itself, PHANTOM's novelty. The store instead builds a combination of image/PURL-scoped behavioral contracts, a typed time-decayed graph, and an plain causal-estimation eli-\\gibility pathway; the current check doesn\textquotesingle t establish that this combination boosts attribution. Anchore Enterprise uses SBOM-centered assessment for vulnerability and supply-chain management {[}12{]}, while Ox Security describes software supply-chain risk analysis across the development and production contexts {[}13{]}. Those capabilities tackle fundamental inventory and risk ques-\\tions. PHANTOM focuses on a narrower gap: the package can remain in the SBOM under the same name and version while its runtime behavior changes. Both artifact identity and live behavior are therefore needed by a solid response, with uncertainty retained when an event can\textquotesingle t be mapped confidently to a component. This difference matters because package identity is not a behavioral invariant. A PURL normally spots package type, namespace, name, and version; it doesn\textquotesingle t prove that a rolled out file is byte-for-byte same to reviewed source or artifact. Stronger provenance can be established by digest pinning and signature verification, but even a validly signed package may include harmful code, as supply-chain incidents have showed. Runtime note adds to those controls by inspecting what loaded software does in the environment where it performs. It can\textquotesingle t replace provenance: an event-to-PURL associ-\\ation is only as solid as the image metadata, process mapping, and file attribution used to make it. These provenance links must be preserved by a practical framework and expose missing links to the analyst rather than silently allocating an event to the nearest package. The same difference shapes PHANTOM's handling of gentle change. Library upgrades, feature flags, configura-\\tion changes, and workload autoscaling can all change event frequencies without showing compromise. A contract trained on one operating envelope may therefore create alerts when a service changes legitimately. Versioned con-\\tracts, workload context, and analyst review are needed to separate routine evolution from suspect drift. We treat contract violation as proof needing explanation, not a verdict that a package is malicious. This policy is chiefly important for services whose legitimate behavior is adaptive or customer-specific. D. Causal Inference Applied to Security Cloud incident root-cause systems combine operational signals to help explain service incidents; RCACopilot, for example, uses an LLM to project a root-cause category and yield an explanation from incident diagnostics {[}14{]}. Earlier host-telemetry research programs also study system-level evidence and provenance {[}18{]}. Graph-based anomaly detection similarly uses relationships among items to spot patterns that are diﬀicult to see in separated events. Applying a broad causal-inference library to runtime evidence is an integration; novelty depends on the graph construction, identification checks, mapping quality, and evaluation rather than the use of DoWhy alone. The difference is between gathering a component substitution and inter-\\vening on that substitution while identifiedly adjusting set fixed. PHANTOM uses Pearl's intervention notation and DoWhy's causal workflow to represent assumptions behind a component-level estimate {[}15{]}, {[}16{]}. An anomaly score or ranked explanation doesn\textquotesingle t by itself spot an intervention effect. SBOM generators establish inventories; vulnerability scanners connect inventories to advisories; runtime mon-\\itors collect events and apply policies; incident tools match up operational signals. PHANTOM targets the in-\\terfaces among these layers, so it doesn\textquotesingle t replace prove-\\nance verification, vulnerability management, or runtime enforcement. Eval-\\uation should compare contracts keyed only by PURL with models regulated on workload role or service mode, and should compare temporal Markov models with frequency baselines using matched event access. Contract generalization remains an open question. The repo uses PURL identifiers as component keys, following the package URL specification {[}26{]}. E. \subsection*{D. RQ3: PCEPS Prediction}
The PCEPS source is implementing feature extraction, XG-\\Boost training, Platt scaling, Brier/ECE calculations, and scoring. No trained PCEPS model, calibration artifact, scored windows, labels, or metric output supporting the manuscript\textquotesingle s former AUC/Brier values was found. No predictive-performance result is mainly reported. The score\textquotesingle s future-outcome interpretation requires a separate prospec-\\tive evaluation. E. RQ4: Overhead The saved CPU, the main processor and memory, alongside event-lag snapshots are all zero. No raw Prometheus samples or measurement

provenance are accompanying them; these entries cannot es- tablish zero resource cost or a particular event-loss rate; runtime overhead is remaining unmeasured, at least in practice; indeed, f. Suggested Benign-Control Protocol Benign controls are needed to estimate how often ordinary workload changes trigger the event or contract pipeline, to a significant degree. False-positive rate, precision, specificity, and F1 are undefined; an event-positive fraction of 6/6 is not a recall estimate, because its event oracle does not need a correctly credited attack, until these runs are collected; these three scenario classes are a suggested protocol, not checked existing runner functionality. A future study should encompass routine package modifies, load changes without component changes, and pod restart/autoscaling episodes; these controls should use the same observation duration and instrumentation as attack runs, with labels fixed before examination; the project repo and saved experiment set do not establish that benign-update, benign-load, and benign-restart au-\\tomation has been applied or carried out. A future check should pre-register the workload, contract ver-\\sion, event labels, and alert threshold, then repeat each class under the matched workload and rollout conditions; sample size should be picked from the desired confidence interval rather than treating three runs per class as automatically suﬀicient. The current data support only that drift events were recorded during six completed attack windows; and thus, they do not bound harmless alert rates or establish attack detection exactness. The three failed SolarWinds-style injections must be fixed and rerun before that attack family can, as it stands, be assessed, and g. Threats to Validity The six completed runs cover two attack families and use a run-level event-presence label; event presence does not establish that a malicious event was, put simply, credited to the injected component. The baseline log documents a dry run, including Falco and Trivy setup were skipped and Falco alert logs were missing. Three attack injections failed. No benign controls, all-zero extra costs snapshots, unresolved component identity, and no reproducibility clear with kernel/runtime versions and image digests are had by The raw data; trivy is a static vulnerability scanner, so a runtime detection comparison needs a separately defined task and labeling rule. PCEPS model/calibration outputs and causal ground-truth comparisons are absent, so these gaps prevent claims of comparative accuracy, causal attribution quality, calibration and operational running costs; and thus, the causal projection also hinges on caller-supplied covariates, hard-coded semantic tiers, and a DAG that includes treatment-to-outcome and covariate edges by construction. The resulting estimate is conditional on those assumptions; neither temporal precedence nor a graph path is proving causation; the gathered event latency cannot be generalized to rollout performance without matched controls, repeated workloads, and recorded environment details. The attack sample is small, run-level labels measure event presence rather than correctly credited compromise, and failed injections are left out, and existing tests exercise spec-\\ified abstention paths, but do not test causal correctness against intervention ground truth. VI. Conclusion PHANTOM is showing an applied pathway that is connecting SBOM-facing contract generation, eBPF event collection, typed graph maintenance, and a causal-\\estimation interface with plain abstention; the immediate evaluation priorities are gentle con-\\trols, per-run component-ground-truth entries, repeatable SolarWinds-style injections, matched baseline output, and a trained PCEPS model found on held-out labels. A local run of the core and five service test suites completed with 454 tests passed and one skipped; this checks exercised software behaviors, not the validity of component-level causal claims in a live rollout; indeed, event-positive outcomes in six completed runs are shown by The experiment records, but do not prove package mapping, attribution accuracy, possible risk prediction, gentle false-positive behaviour, or overhead. Kernel, Kubernetes, container runtime, tool versions, image digests, and experiment commit must be recorded with the rerun; indeed, no claim is made that the infrastructure for all these experiments is already applied or ready to carry out. Supply-chain incidents expose a gap between declared software inventory and gathered runtime activity; and thus, PHAN-\\TOM looks into one way to represent that gap while making missing identity and failed causal identification visible to an analyst. Its present insight is an used research prototype and an auditable account of what the available tests and six successful attack runs do, and do not, show; in fact, controlled check must establish whether its component-scoped contracts and causal pathway pro-\\duce solid attribution beyond event detection.
